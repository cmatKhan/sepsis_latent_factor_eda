Running the workflow

Running the pipeline

The main process – tar_make() – coordinates: it submits SLURM worker jobs through crew.cluster and must stay alive until they finish, because workers connect back to it.

As a batch job (anything long, e.g. a full build):

sbatch run_pipeline.sbatch                                     # everything outdated
sbatch run_pipeline.sbatch 'tidyselect::starts_with("fit_")'   # fits only (no ingestion)
sbatch run_pipeline.sbatch 'tidyselect::starts_with("db_")'    # rebuild DB rows from stored results
tail -f logs/targets_main_<jobid>.out

The argument is passed to tar_make(names = ...). targets builds the named targets plus whatever they depend on, and nothing else, so a part of the pipeline can run without the long fits. For example, the repeated-measures analysis alone for every dataset:

sbatch run_pipeline.sbatch 'c(starts_with("design_"), starts_with("expr_"), starts_with("norm_"),
  starts_with("vp_"), starts_with("dream_"), starts_with("de_tables_"), starts_with("dupcor_"),
  starts_with("composition_"), starts_with("controls_"), starts_with("control_factor_"),
  any_of("variance_explore"))'

Check tar_outdated(names = ...) with the same selection first: it lists exactly what would build.

From RStudio Server on the cluster, open the project and use the console:

library(targets)
tar_visnetwork()                            # the graph, outdated targets highlighted
tar_outdated()                              # what tar_make() would rebuild
tar_make()                                  # build everything outdated
tar_make(names = starts_with("fit_pca_"))   # a subset
tar_make(as_job = TRUE)                     # as an RStudio background job
tar_progress_summary()                      # progress while a run is going

An interactive session ends with its SLURM job (16 h at most on interactive), so long runs belong in run_pipeline.sbatch.

Reading results: tar_read(fit_pca_EARLI) returns a target’s value. read_method_fits("EARLI", "spca") (R/targets/run_method_fit.R, available after targets::tar_load_globals()) returns a method’s fits as one list(params, result) per grid row, both sPCA stages included.

What reruns when

targets reruns a target when its command, its inputs or a function it calls changes (comments and whitespace don’t count).

Change Reruns
a dataset’s config, preprocessing script or raw files that dataset only
a method’s grid in one config (e.g. adding a rank) only the new grid rows’ fits, then that dataset’s ingestion
a method’s fit function or <name>_registry every fit of that method (sPCA: about a day)
run_method_fits(), fit_subjects(), the grid helpers, capture_fit() every fit of every method that uses them
a dataset’s design: block, R/lib/design.R or R/targets/variance*.R that dataset’s repeated-measures targets and score-level partitions, then its DB write – never a fit
a controller’s batch_size or cpus_per_task that method’s fits (they change the grid)
a controller’s memory, time or worker settings nothing
a method’s <name>_ingest or the ingestion code in R/targets/ ingestion and the DB writes only
R/db/schema.sql or views.sql the DB writes (after deleting the DB, see Database)

Stopping a run keeps every finished branch. Removing a dataset from config/pipeline.yml leaves its results in the store (targets::tar_prune() deletes them).

SLURM resources

Each method has a crew controller under controllers: in config/pipeline.yml: memory, CPUs, wall time, idle timeout, batch_size, tasks_max. Ingestion, enrichment (fgsea), projections (projectr) and matrix building (prep) have their own. Each controller grows its pool of worker jobs with the backlog and shrinks it when work runs out; a worker is one SLURM job that runs tasks until it’s idle or reaches its time limits.

  • No worker caps by default. SLURM’s scheduler and per-user limits (200 running jobs per user on HTCF) decide what runs when; a controller without workers: is effectively uncapped. PCA, NMF and ICA keep small caps for efficiency: their tasks take seconds, much less than a worker’s ~30 s R start-up, so one worker per task would mostly be start-up.
  • Batches. Each branch costs the main process about a second of bookkeeping, so fast methods group grid rows into branches (batch_size), and projections run one branch per (source, target) dataset pair.
  • Backups for out-of-memory. A controller’s backup: block (crew backup controllers) retries a task whose worker crashed crashes_max times – typically killed for exceeding memory on the largest datasets – on <name>_backup with more memory.
  • One fit per worker for long fits. sPCA and the vp controller (variancePartition and dream, BiocParallel MulticoreParam over cpus_per_task) use tasks_max: 1, so no long task starts late in a worker’s life.

Main-process memory

The main process’s memory scales with the number of tasks it has handed to crew and not yet collected, not with the data:

  • Every ready task is pushed at once. targets pushes a ready target to its controller unless the controller is saturated (crew’s saturated(): tasks pushed ≥ workers); a saturated controller’s targets wait in targets’ own backlog as names. Without a workers: cap a controller never saturates, so every ready task is pushed immediately, including the ones waiting in SLURM’s queue behind the 200-running-jobs limit.
  • Each pushed task carries the globals. The payload is the target plus every object and function that _targets.R and R/ define: about 5.3 MB serialized (2026-10-14), mostly source references. tar_source() parses with keep.source = TRUE; without them it’s 0.44 MB.
  • It’s held in the main process. mirai’s dispatcher is a thread in the main R process (mirai ≥ 2.7), so each outstanding task costs about twice its payload, ~10.6 MB.

The full run’s opening burst (2026-10-14: about 1,400 tasks, mostly CoGAPS, WGCNA and sPCA, as every dataset’s grids became ready together) took the main process to 14.75 GB within two minutes, and 16.8 GB after twenty. That burst crashed a run with --mem=16G; run_pipeline.sbatch requests more, and up to about 20 GB is acceptable on HTCF. The script also writes logs/targets_main_<jobid>_mem.tsv (the job’s memory, each process’s RSS and the number of worker jobs, every 30 s).

If it becomes a problem, shrink the payload rather than cap workers (a cap below the cluster’s running limit leaves capacity unused when one controller has the remaining work). The targets manual recommends putting a large project’s functions in an R package: each task then ships only the package name, and workers load it. Sourcing R/ without source references would also cut the payload about twelvefold; targets hashes functions without them, so neither change reruns anything.

Expected resource use

Measured on the full runs of 2026-10-14/15 (35 datasets, 19-991 samples; matrices are capped at 8,000 genes, most have 7,000-8,000). Each dataset is one observation: times are fitted as log(seconds) ~ log(samples) + log(genes) [+ log(rank)] [+ para], so the exponents below say how a step scales. Memory is the SLURM peak (MaxRSS) of worker jobs that did work, or the task’s own cgroup record on the vp controller. sPCA dominates: a dataset’s sPCA costs a median 20 CPU-h (largest 87 CPU-h). Per-fit time barely depends on the number of samples, because spca() works on the gene × gene covariance: genes and the sparsity para drive it. Fits at high K and para on the largest datasets reach the 8 h cap (4 fits on 2026-10-14: ANEMONES K 10 para 0.55; MARS K 8-12 para 0.40-0.45), so a run’s wall time is about two 8-hour stages (scan, then refine) for the slowest dataset, not the total CPU-hours.

Tuning

Aim for about 75% average memory and CPU use, never below 50%, and err on the high side. Size memory for the largest dataset (SHIP-TREND: 8,000 genes × 991 samples), not EARLI.

  1. Run the method, e.g. tar_make(names = starts_with("fit_nmf_")).
  2. Find the worker array ids: sacct -X -S <start> --format=JobID,JobName | grep crew-worker.
  3. Check usage with seff <jobid>, or for an array python /scratch/mblab/chasem/seff-array/seff-array.py <array id>. seff-array needs a terminal; from a non-interactive shell wrap it: script -qc "stty cols 100; python .../seff-array.py <id>" /dev/null.

The vp controller also records its own use: norm_, vp_ and dream_ store their job’s cgroup peak memory and CPU seconds in their result ($resources, job_resources() in R/targets/variance.R), and vp_summary_<key> reports them. That was needed when these tasks used socket (SnowParam) workers, which left the job’s process tree so seff missed them; since 2026-10-14 they use forked (MulticoreParam) workers, which use no ports. seff still misses them: on the 2026-10-14/15 runs SLURM reported a median CPU efficiency of 0.02 for vp jobs, while the cgroup records show about 90% of 8 cores (e.g. vp_ANEMONES: 5,829 CPU-seconds in 795 s). Use $resources for this controller.

The current values and the measurements behind them are in config/pipeline.yml’s comments.

Running on a scheduler other than SLURM

The pipeline has only run on SLURM (HTCF). The targets themselves don’t depend on that: they only name a controller (tar_resources_crew(controller = "prep") in R/targets/factories.R), so the pipeline’s logic is the same on any crew backend. Six things are tied to SLURM, and a port would change these:

  1. Controller construction. build_controller_group() (R/targets/controllers.R) is the only place controllers are built, and it calls crew.cluster::crew_controller_slurm() with crew_options_slurm(). The other crew.cluster schedulers (SGE, PBS, LSF) have their own controller and options functions, and crew::crew_controller_local() runs everything on one machine (useful for tests).
  2. The controllers: block. Its fields map onto SLURM: time_minutes is the job’s --time (and sets the soft wall time, seconds_wall), memory_gigabytes_required and cpus_per_task are the job’s resources, and partition (under cluster:) is the SLURM partition. Other schedulers name and limit these differently, and the comments in config/pipeline.yml reason about SLURM’s behaviour (jobs killed for exceeding memory, per-user job limits).
  3. The worker environment. worker_script_lines() (R/targets/controllers.R) puts R on each worker’s PATH from the spack environment in the cluster: block, then changes into the project directory so renv activates. cluster.setup_lines replaces the spack lines with whatever provides R elsewhere.
  4. Starting the run. run_pipeline.sbatch is a SLURM script that runs the tar_make() main process. Any way of keeping that process alive for the whole run works, because the workers connect back to it.
  5. Resource recording. job_resources() (R/targets/variance.R) reads the job’s cgroup (v2) under slurmstepd.scope, using SLURM_JOB_ID. Outside SLURM, or without cgroup v2, it returns no usable measurement; the vp tasks’ $resources would be empty.
  6. Names and comments. The method registries’ resource_defaults() take an argument called slurm_cfg (only cpus_per_task is read from it), and comments and docs mention SLURM and HTCF throughout.

A port is therefore mostly a rewrite of build_controller_group() and the controllers: fields, plus items 3 to 5. The resource numbers in config/pipeline.yml were tuned on SLURM and would need tuning again.

Logs and monitoring

What Where
main process logs/targets_main_<jobid>.out
main-process memory logs/targets_main_<jobid>_mem.tsv (every 30 s)
workers logs/crew/<controller>_<jobid>.out
per-target errors and warnings tar_meta(fields = c(error, warnings))
progress tar_progress_summary(), tar_poll()

A failed fit doesn’t fail its branch: it’s recorded with status = 'failed' and its error in the DB. A target that does error is skipped along with what depends on it, and the rest of the run continues (error = "continue").

Rebuilding the database

targets::tar_invalidate(starts_with("db_")); targets::tar_make()

After a schema change, delete the DB file first (only the .sqlite: the schema is versioned and an old DB is refused). Keep stability_artifacts/, which ingestion wrote and won’t rewrite. Nothing upstream reruns.
